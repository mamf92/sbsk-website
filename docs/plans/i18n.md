# Plan — Norwegian and English for the member, admin and legal pages

Status: planned · Owner: unassigned · Builds on: the i18n foundation in the event-pages plan
(`docs/plans/01-event-pages.md`, work package WP2) · Used by: [phase 2](phase-2-admin-page.md),
[phase 3](phase-3-members.md), [GDPR](gdpr.md)

The **foundation is owned by the event-pages plan** and lands first. This document does not
redefine it; it adds what the signed-in parts of the site need on top. If the two ever
disagree, the foundation wins and this file is updated.

## The foundation, for reference (do not re-implement)

- i18next + react-i18next. `nb` is the default and the source of truth; `en` second.
- No `/en/` prefix; Norwegian slugs stay byte-identical (`CLAUDE.md`).
- Header toggle; preference in `localStorage['sbsk-locale']`; `<html lang>` set by one module.
- Namespaces `common` and `events`, bundled JSON in the repo, lazily loaded.
- Sanity visitor text as `{ nb, en }` objects (`localeString` / `localeText` / `localeBlock`),
  `en` optional, falling back to `nb` rendered with `lang="nb"`.
- A key-parity unit test (every key in both languages, no empty values).

## What this plan adds

### 1. Namespaces

| Namespace | Holds                                                                                   | First used in |
| --------- | --------------------------------------------------------------------------------------- | ------------- |
| `auth`    | Login, OTP code entry, "lag medlemsprofil", MFA prompts (shared with the security plan) | Phase 2       |
| `admin`   | Styreportal: overview, members, check-in, statistics, every edge-function error code    | Phase 2       |
| `member`  | Min side: dashboard, calendar, badges, membership card, settings, privacy section       | Phase 3       |
| `legal`   | Privacy policy and terms, long-form, versioned (see [gdpr.md](gdpr.md))                 | Phase 3       |

Keys are semantic and nested (`member.stats.checkIns`, `admin.errors.last_admin`). Badge names
and descriptions live under `member.badges.<slug>.name` / `.description`, keyed by the badge's
slug in the database, so adding a badge means adding a row **and** two keys in each language —
the parity test then also checks every seeded slug has keys (read the slugs from the seed SQL
file in the test).

### 2. The language follows the member, not only the device

- New column `profiles.locale` (`'nb' | 'en'`, default `'nb'`), added in phase 2 step 1.
- On sign-in: if the device has an explicit stored preference, it wins and is written to
  `profiles.locale`; if not, the profile's value is applied to the device.
- Changing the toggle while signed in also calls `updateProfileLocale(locale)`
  (`src/supabase/queryHelpers/updateProfileLocale.ts`).
- Why: invite emails, OTP emails and push notifications (PWA plan) are sent server-side and
  must pick the member's language without a browser to ask.

### 3. Server-sent text

- **Auth emails** (invite, OTP code, email change): Supabase sends one template per type and
  has no per-user language. Write each template **bilingual** — Norwegian first, English below a
  divider — in `supabase/templates/*.html`, and configure them in `supabase/config.toml`
  (`[auth.email.template.invite]` etc.) so they are versioned. The OTP template must contain
  `{{ .Token }}` (a 6-digit code), not only the link (see phase 3 decision 3).
- **Edge-function errors** return stable codes (`not_admin`, `last_admin`, `no_mfa`,
  `export_rate_limited`, …), never prose. The UI maps codes to `admin.errors.*` /
  `member.errors.*`; an unknown code shows `common.errors.generic`.

### 4. Forms and validation

Zod schemas become factories that take `t`, so messages follow a language switch without a
reload: `makeProfileSchema(t)`, `makeMemberEntrySchema(t)`, `makeMarkPaidSchema(t)`. Apply the
same to the existing `src/schemas/contact.ts` when the contact-form plan touches it.

### 5. Formatting

Dates, times and money through `Intl` with `nb-NO` / `en-GB` (day-month order, 24-hour clock in
both). Put the helpers in `src/utils/format.ts` if the foundation has not already:
`formatDate`, `formatTime`, `formatDateRange`, `formatNok` (`Intl.NumberFormat(locale, { style:
'currency', currency: 'NOK', maximumFractionDigits: 0 })`). Member since: month + year.

### 6. Legal pages

Translated **in full**; a member must be able to read what they agree to in a language they
understand. Each language version carries the same version id (`2027-01`), and the acceptance
stored on the profile records the version, not the language. Both live in `legal.json` as
structured sections (heading + paragraphs + lists), rendered by one `LegalDocument` section
component, so no HTML is stored in JSON. Links inside a paragraph use `<Trans>` with named
components.

## Tests

- Extend the foundation's parity test to the four new namespaces, plus: every badge slug in the
  seed migration has `name` and `description` in both languages; every error code the edge
  functions can return (exported as a `const` array from `supabase/functions/_shared/errors.ts`
  and mirrored in `src/utils/errorCodes.ts`) has a key.
- `updateProfileLocale` helper test; the sign-in sync rule (device wins when set).
- `renderWithI18n` test helper (if the foundation has not added one) with both languages
  bundled synchronously.
- e2e: on `/medlemsportal` and `/styreportal`, switch to English and assert no raw keys
  (`/^[a-z]+(\.[a-zA-Z_]+)+$/`) are visible; reload keeps English.

## Acceptance

- Every string on login, Min side, Styreportal and the legal pages comes from a namespace.
- Parity test green; `npm run build` type-checks keys.
- A member who picked English on their phone gets English on a fresh laptop after signing in.
